# Unattended queue run — `node scripts/autobuild.mjs [<n>]`

A script the user launches from a terminal (not an agent) drains the build queue (`gh-project.mjs queue`: top-level not-Done items, In progress then Todo, board order) item by item: a fresh headless `claude -p "/build #n" --model haiku --permission-mode auto` per part, then it waits for green CI on the PR, squash-merges it (`--delete-branch`), syncs `master` and moves on. An item is an epic (its open parts in order, then the epic is closed and set Done) or a standalone issue (built like a one-part epic). It is the single place where something other than the user merges.

- **Plan:** the plan printed at the start is a preview; the queue is re-read before every part and the run builds the next part of the top item, so started (In progress) work is always finished first and a new P0 waits for it; the log says `kontynuuję rozpoczęte: #n` for a started item and `pominięto ręczną kartę #n` once per manual card. A closed item is skipped. `--items N|all` (default all) counts distinct started items - an epic in flight is always finished, even when a P0 appears. An In progress item without the `autobuild` label is a manual build (`ręczny`) and is skipped unless `--include-manual`. `autobuild.mjs <n>` plans only `#n` - an epic or a standalone issue, manual or not; a part stops `usage` with `#n is a part of epic #m`, a Done item gives an empty plan. An empty plan ends `done` (`kolejka pusta`, no shutdown). Before a part's build `autobuild.mjs` adds `autobuild` to the item and the part, which also claims a manual item it was told to take.
- **Start and window:** `--start now|MIN|HH:MM` keeps the PC awake from launch and begins the work (preflight included) at that time (HH:MM = the next occurrence). `--until HH:MM` is the window end, the next occurrence after the start: no `claude -p` session (`/build`, `/fix e2e` or `/fix ci`) starts at or after it; one already running finishes, its CI wait and merge still run, then the run ends with reason `window`. `--max-tasks` counts builds across the whole run.
- **Needs:** a clean working tree (or uncommitted changes on the first item's next part's own branch with no open PR - an interrupted build, resumed; anything else stops `dirty-tree`), `preflight.mjs` passing, the WSL runner online (otherwise CI never starts - `runbooks/ci.md`). A part without a Branch field is healed (`gh-project.mjs heal`) and built. `--dry-run` prints the numbered plan (`ręczny` marked), the start time, the window end and per item's part what would happen (skip / CI → merge / build / resume build / retry ship / waits), and the runner, and changes nothing.
- **Migration guard:** `autobuild.mjs` itself still never reads an issue body, but a part whose migration destroys protected data without the ticket's `## Utrata danych` / `## Przeniesienie danych` consent (or rewrites an existing migration) fails `verify.mjs` and `ship.mjs`, so no PR exists and the run stops `blocked`, the report naming the missing keys and sections.
- **Test plan upkeep:** `autobuild.mjs` never reads or writes an issue body (only its e2e repair, below, may rewrite the epic's plan). Each part's `/build` updates its own `## Test manualny` on deviation, and the last part's build (every other sub-issue closed) refreshes the epic's plan, exactly as a manual `/build` does.
- **Resume:** there is no state file. Every iteration re-reads the epic from GitHub: a CLOSED part is skipped, a part with an open PR goes straight to CI + merge, otherwise it is built. An interrupted build is built again on the tree on disk (`/build` continues from the existing changes, the pipeline reruns from tests). If the newest comment on the part is a blocked report at `ship` and HEAD is its branch, only `ship.mjs` is retried (not counted as a build). A build session that ends with no PR, no new comment on the part and a `ready` workflow run newer than the build start (the relay never ran `nextCommand`; ship.mjs comments on every run) is shipped by `autobuild.mjs` itself with `ship.mjs <n> --from-run`. Re-running the same command after any stop continues where it stopped.
- **The e2e part in an unattended run:** it is built like any part. When the newest comment on it is a blocked report at `e2e`, the plan is a fresh `build` (the tree was cleaned and `prepare` recuts the branch from master); a build that ends blocked at `e2e` is repaired without the user. `environment`: `stop-stack.mjs`, then the e2e part is rebuilt once per run. `app`: a headless `claude -p "/fix e2e:#<n>" --model claude-opus-5-5` reads the block, reproduces below the browser and decides which side is wrong - the app (it publishes `Fix:` part(s) with `create --parent <epic> --before <n>`, so the loop builds, CI-checks and merges them before rebuilding the e2e part) or the epic's plan (a part's AC specifies what the app does; it rewrites those steps of `## Test manualny` and comments the epic) or the test (through the API and after a reload the app reaches the plan's value within 30 s, and the test waits wrongly, does not re-fetch or selects wrongly) - and ends with a `FIX_RESULT:` line (kind `app`, `plan`, `test` or `stop`). For `test` it changes no file and comments the part with a diagnosis whose first line is `**E2E test defect** — <test>, Krok <k>` (what is wrong, the evidence, the fix hint; never a changed expected value). The diagnosis is the part's newest comment, so the next build of the part - from `autobuild.mjs` or a manual `/build #<n>` - reads it: `prepare` writes it to `skarbiec-plan/issues/<n>.diagnosis.md`, applies the saved `<n>.e2e.patch` (after `git apply --check`) onto the fresh branch and passes `workflowArgs.diagnosis` and `patchApplied`; the e2e agent then fixes only how the diagnosed steps wait, re-fetch or select, and the reviewer blocks a changed expected value or plan assertion compared with the patch. A value that never arrives, arrives after more than 30 s or differs from the plan is `app`. An unknown `FIX_RESULT` kind stops the run (`blocked`). The run stops with reason `e2e app` / `e2e environment` and the trace path when the repair stops (no reproduction, a missing design, a harness cause), after the 3rd app block on one part - `app`, `plan` and `test` repairs share that one limit - or on a second environment block in the run.
- **CI rerun:** a red CI is restarted before anything is repaired - most reds are flaky tests or infrastructure. Whatever failed (a test job, a build, a cancelled/timed-out job, any number of failed tests), `autobuild.mjs` waits until no check is pending, calls `POST actions/runs/{id}/rerun-failed-jobs` once per head SHA and logs `CI PR #501: 1 test failed (reporting) — rerun failed jobs` (the failed-test count, VSTest `Failed!  - Failed: n` lines summed or Vitest `Tests  n failed`, only decorates the line; job logs are read with `gh api --allow-escape-sequences` because gh refuses logs with ANSI codes). GitHub's `run_attempt` is the only counter (nothing is kept locally, so a resumed run does not rerun a run already at attempt 2); the wait after the rerun ignores the stale red until `run_attempt` rises or a check is pending again, has its own fresh 90 min budget and does not count towards `--max-tasks`. A job at `run_attempt >= 2` (red after the rerun) or with no workflow run to rerun starts the CI fix below (and stops `ci-failed` once the fix is spent). The part line and the summary read `(build 15 min, CI 9 min, CI rerun 1)`; `--dry-run` prints `CI: rerun failed jobs once per head commit, then one fix session per PR`. Code: `scripts/autobuild-ci.mjs`.
- **CI fix:** a red CI that is still red after the rerun gets one fix session per PR instead of stopping. Once no check is pending, `autobuild.mjs` logs `CI PR #501: red after rerun (reporting) — fix session 1`, switches to the PR branch (clean tree required; a dirty tree on the PR branch is an interrupted fix and is kept; any other dirty tree stops `dirty-tree`), runs `claude -p "/fix ci:#<part>" --model claude-opus-5-5` and switches back to `master`. Guards as for an e2e repair: the stop file ends the run `stopped`, a closed `--until` window ends it `window` with the `resume:` line, `--dry-run` starts nothing; the session is not a build and never raises the `--max-tasks` count. A usage limit during the session sleeps to the reset (`--on-limit` as for a build) and reruns the same prompt on the tree as it is; `timedOut` stops `timeout`. `/fix ci:#<n>` (see `.claude/skills/fix/SKILL.md`) reads `node scripts/ci-digest.mjs <pr>` (failed jobs, failed step, the last ~200 log lines of it, the failed test names), the part's Goal / ACs / Code map and the PR diff, finds the cause and runs the `build-feature` workflow on the existing branch with the profile *implementer → reviewer* (the red job is the reproduction, no test-writer, `args.ciFix` carries the failure; the reviewer blocks a fix that silences the failure: a deleted, skipped, weakened or timeout-widened test without a stated cause), then `ship.mjs <n> --fix-pr` and the last line `FIX_RESULT: {"ok":true,"kind":"ci","summary":"…"}` (or `{"ok":false,"kind":"stop",…}`). The PR comment with the hidden marker `<!-- skarbiec-ci-fix -->` is the only "fix used" state, so a resumed run never fixes twice. Afterwards autobuild checks that the PR head moved and the marker comment exists (else `blocked`), then waits for CI again with its own 90 min budget: green merges as usual, red reruns once more (the new head has its own `run_attempt`), a red after that stops `ci-failed` with the job link, `(rerun n, fix 1)` and the `resume:` line. A session that returns `ok:false` stops `ci-failed`. The part line reads `(build 15 min, CI 9 min, CI rerun 1 · fix 1)`. Never a second fix, a fix on a PR opened by hand or a merge-conflict repair. Code: `scripts/autobuild-ci.mjs` (`runCiFix`), `scripts/ci-digest.mjs`.
- **Stop reasons** (the epic gets a comment with the parts done, the reason and the detail; exit 2 except `done`): `done` (every part merged; the epic is closed and its card set to Done), `stopped` (stop file), `max-tasks`, `window` (the `--until` time passed - no new build), `e2e app` / `e2e environment` (the e2e part is blocked), `limit` (`--on-limit exit`, or the limit hit during an e2e repair), `limit-unknown` (the build hit the Claude usage limit and its stream carried no reset time), `limit-too-far` (the reset is beyond `--max-wait`, e.g. the weekly limit), `wake-not-ready` (after the limit wait the PC was not ready within 15 min), `blocked` (the build opened no PR - its report is on the issue), `timeout` (build over 4 h of awake time), `hang` (the same part made no progress for 45 min twice), `ci-failed`, `ci-missing` (no checks after 10 min), `ci-timeout` (90 min), `ship-failed` (the retried ship step failed again), `merge-failed`, `sync-failed`.
- **Skipped cards:** a card whose Tier is missing or not 1/2 cannot be repaired by a script, so it never stops the run: `autobuild.mjs` logs `pominięto #n: brak Tier`, posts one comment on it (hidden `skarbiec-autobuild-skip:<n>` marker, so a later run does not repeat it), leaves its Status and takes the next card. The later open parts of its epic and every queue card whose `Depends on` names a skipped card are skipped the same way (`pominięto #m: zależy od #n`). A run that only skipped cards ends `done`, exit 0, and its closing lines list them (`pominięte: #466 (brak Tier), #467 (zależy od #466)`). A skipped card is re-evaluated by the next run and builds as soon as its Tier is set.
- **GitHub budget:** CI is polled over REST (the PR head's check runs; a failed read is logged, never counted as "no checks"), the project is read over GraphQL. The log has a `GitHub: GraphQL <remaining>/<limit>, REST <remaining>/<limit>, reset HH:MM` line at the start and end of each part (and in `--dry-run`); `prepare` stores the start snapshot in `.git/gh-usage-start.json` and the run report carries one line with it and the snapshot at report time.
- **GitHub limit:** `scripts/gh.mjs` classifies a failed `gh` call (`primary-graphql`, `primary-rest`, `secondary`, `transient`, `other`; unclear text counts as primary when `rate_limit` shows that resource at 0). `autobuild.mjs` is the only script that waits, with no upper bound: it logs `limit GitHuba (<kind>), czekam do HH:MM`, sleeps until the reset plus 30 s (a secondary limit: 60 s doubling to 15 min), logs the resume and repeats the same call or step. A `/build` stream carrying a `GITHUB_LIMIT` line (a script inside it exited 4) or a `ship.mjs` exit 4 is waited out and the step rerun (the workflow journal replays what the build finished). The wait counts towards neither the build nor the CI timeouts, and the heartbeat keeps logging. Before a write is repeated after a wait it is checked: a merged PR is not merged again, a closed issue not closed again, the run summary and the build report (hidden `skarbiec-run` marker: issue, branch, head, report digest) not posted twice. The Claude usage limit is a separate wait (below). Interactive scripts (`gh-project.mjs`, `ship.mjs`, `gh-usage.mjs`) never wait: they print `Limit GitHuba (<kind>) wyczerpany, reset o HH:MM` and a `GITHUB_LIMIT` line on stderr and exit 4; `plan-status.mjs` and `idea.mjs context` print `limit GitHuba do HH:MM` in place of the board.
- **Start wizard:** when stdin and stdout are a terminal (`--dry-run` too), `autobuild.mjs` asks every setting no flag answered, in order: the plan (the numbered queue, `--items`, skip manual items - only when the plan has one), the limit behaviour (`--on-limit`, with the wake-timer state, option a) marked unavailable with the hint when timers do not work; then `--max-wait`), shutdown after the run, the start (`--start`) and the window (`--until`). A flag (or the positional number, for the plan) skips its question; Enter takes the shown default; an invalid answer is explained and asked again. Then it prints a summary (with the resolved start and window end date and time), the equivalent command and one `Start? [T/n]` (none when no question was asked). `n` exits 0 and Ctrl+C exits 130; either way nothing starts - no log, keep-awake, comment or shutdown. Without a terminal nothing is asked and the defaults apply. Code: `scripts/autobuild-wizard.mjs`.
- **Stop it:** `node scripts/autobuild.mjs --stop` (a number is ignored) creates the one stop file `%TEMP%/skarbiec-autobuild.stop`; the driver finishes the part in flight and stops before the next build. Ctrl+C kills the build's process tree at once (exit 130, no comment, no shutdown).
- **Logs:** one plain-text file per run, the gitignored `skarbiec-plan/autobuild-runs/<YYYYMMDD-HHMMSS>.log`, with exactly the lines the terminal shows (`HH:MM  ` + event: phase, agent type and model, start/done with tokens and time, background commands as `bg: <label>` / `bg done|failed|killed: <label> · <time>` (a label such as `weryfikacja (verify.mjs)`, `pełny zestaw e2e` or the agent's own description, never the raw command), CI, merge, a `still:` line after 10 quiet minutes). The `still:` line ends with what the agent is doing: `teraz: <label> (od N min)` from the last subagent tool call, `teraz: brak nowych narzędzi od N min` when it only thinks, `czeka na proces w tle od <time>` when a background command runs and the token and tool counters did not grow since the previous heartbeat, `bez postępu od <time>` when they did not grow and nothing runs in the background (a message only; the 45 min hang rule is separate). Code: `scripts/autobuild-activity.mjs`. The raw stream is not kept; each build prints its session id, and `claude --resume <session>` opens the full conversation. `--permission-mode auto` can deny a tool call without anyone to answer: that prints `DENIED: <tool>` and the build's last line counts the denials.
- **Power:** on Windows a hidden PowerShell child holds `SetThreadExecutionState` (`ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED`) from launch while the run lasts, re-asserting it every 30 s and printing `ready` once the call succeeded, so idle sleep, display-off and the idle lock are blocked; the log says so only after that confirmation, otherwise `UWAGA: blokada snu nie działa (<reason>)`. The guard is killed, restarted and confirmed again (one retry, then the build goes on with the `UWAGA` line and a warning in the closing summary) after every wake from the Claude limit and after the deferred `--start` wait, before the readiness check. Closing the lid still sleeps the PC. While a `claude` child runs, a 60 s tick detects a PC sleep (a gap above 3 min, logged `PC spał 02:09–05:07 (178 min)`) and the sleep counts towards neither the 4 h build limit nor the hang detector. A build with no progress (no change of tokens or tool calls, no agent event) for 45 awake minutes while its process tree holds no `dotnet`/`testhost`/`vstest`/`verify.mjs`/`e2e.mjs`/`vitest`/`playwright` process (MCP servers do not count) is killed, `stop-stack.mjs` runs and the same part is built again as a plain replay (`zawieszenie: brak postępu 45 min (…) — restart #n`); a second hang of the same part stops the run with reason `hang`, and `hang restarts: N` and the slept minutes close the `done in this run` line. `--start` holds the PC awake from launch but starts the work only at the given time, logging the start time and a line every 10 min; the stop file ends the wait (reason `stopped`, no comment, no shutdown), and so does Ctrl+C. Every sleep, hibernation and end-of-run shutdown is announced by an always-on-top Tak/Nie popup (`Uśpienie|Hibernacja|Wyłączenie za 9:41`, counting down 10 min): **Tak** acts at once, no answer acts when the 10 min run out, **Nie** declines (the PC stays on; a declined sleep is an awake wait). Unless `--no-shutdown` (`--shutdown` is the default) or `--dry-run`, every end of the run, whatever the reason, asks `Wyłączenie za` and then runs `shutdown /s /t 0`.
- **Claude usage limit:** a build's own stream reports the limit and its reset (nothing probes it). `--on-limit sleep|wait|exit` (default `sleep`) and `--max-wait <hours>` (default 12) decide: the wake time is the reset + 5 min; with `sleep` a wait of 15 min or less is awake, under 1 h the PC is suspended, from 1 h it hibernates (suspended when hibernation is unavailable, awake when wake timers are off); `wait` always waits awake; `exit` ends the run with `limit`. An unknown reset ends `limit-unknown`, a reset beyond `--max-wait` `limit-too-far`, and a wake time at or after the `--until` window end ends `window`, all without sleeping. The log says `limit Claude, reset HH:MM — hibernacja do HH:MM` / `uśpienie do HH:MM` / `czekam do HH:MM`. A suspend or hibernate runs a hidden PowerShell with a waitable timer with resume (`powercfg /waketimers` needs admin and is never used), so nothing stays registered if the run dies; the 10-min popup counts towards the wait. After the wake or wait the stop file ends the run (`stopped`), a passed window ends it (`window`); then the PC must be ready - `preflight.mjs`, a `gh` call (the runner list) with the runner online - retried every 30 s for up to 15 min, still failing ends `wake-not-ready`. The same part is then built again (the workflow journal replays what the interrupted build finished); that rebuild does not count towards `--max-tasks`. Wake timers on mains power must be on (`powercfg /query SCHEME_CURRENT SUB_SLEEP RTCWAKE`, AC index 1); the first log lines say `wake timers: on` or `off — <hint>` with the `powercfg /setacvalueindex SCHEME_CURRENT SUB_SLEEP RTCWAKE 1` fix. Check the machine with `node scripts/autobuild.mjs --sleep-test <minutes>` / `--hibernate-test <minutes>`: it suspends or hibernates with a wake timer that many minutes ahead (no popup), prints the planned and actual wake time and `powercfg /lastwake`, and exits.
- **Last lines:** `run: <reason> — <detail>`, the items and parts done in this run (PR, build and CI minutes), `resume: <command with the run's flags>` unless the run is done, and the shutdown notice. The summary comment is posted on every item the run touched. Exit 0 when done, 2 otherwise, 130 on Ctrl+C.
